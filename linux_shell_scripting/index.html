El punto de partida

Qué es un shell script

Cuando escribes ls -l y pulsas Enter, no es el kernel quien te contesta. Es un programa llamado shell que lee tu línea, la interpreta y ejecuta lo que corresponde. En Linux ese programa suele ser Bash.

Un script es exactamente lo mismo pero sin ti delante: un fichero de texto con las órdenes ya escritas, una por línea, que el shell lee de arriba abajo como si las estuvieras tecleando una detrás de otra.

De ahí salen tres consecuencias que conviene tener claras desde el principio:

  • No se compila. No hay un paso de construcción ni un binario resultante. Guardas el fichero y ya se puede ejecutar.
  • La extensión da igual. .sh es una costumbre para que los humanos lo reconozcan; el sistema no la mira. Un script puede llamarse copia a secas.
  • Todo lo que funciona en la terminal funciona en el script, y al revés. Si dudas de una línea, pruébala suelta antes de meterla.

Pruébalo

Escribir el fichero: nano y vi

Antes de escribir un script hay que poder escribir un fichero, y en una terminal eso significa un editor de texto. El examen no pide dominar ninguno: pide saber abrir, escribir, guardar y salir con los dos que siempre están ahí.

nano es el que quieres si acabas de llegar: escribes directamente y las teclas aparecen al pie de la pantalla. El símbolo ^ de esa lista significa Ctrl, así que ^O es Ctrl+O.

vi (o su versión moderna, vim) es feo de aprender pero está instalado en absolutamente todos los sistemas Linux, incluido ese que arranca en modo rescate y no tiene nada más. Por eso hay que saber lo mínimo.

La trampa de vi está en la primera tecla. vi tiene modos. Al abrirlo estás en modo normal, donde las letras no se escriben: se interpretan como órdenes. Teclear «hola» no escribe «hola», sino que ejecuta cuatro órdenes distintas. Hay que pulsar i antes de poder escribir, y Esc para volver.

vi, con las manos

Pulsa las teclas de debajo de la pantalla y mira qué ocurre. El objetivo es que veas el momento exacto en que vi deja de obedecerte y por qué.

La primera línea

      
El shebang: #!

      

        
Un script empieza con una línea que no es una orden:

      



#!/bin/bash


      

        
Esos dos primeros caracteres, # y !, se llaman shebang y los lee el kernel, no el shell. Cuando le pides ejecutar un fichero, el kernel mira sus primeros bytes: si encuentra #!, entiende que no es un binario sino un guion, toma la ruta que viene detrás y arranca ese programa pasándole el fichero como argumento.

        
Es decir, ./copia.sh acaba convertido en /bin/bash ./copia.sh sin que tú lo escribas.

        
La elegancia del truco está en que # es también el carácter de comentario de Bash. La misma línea significa algo para el kernel y es invisible para el intérprete: nadie tropieza con ella.

      


      

        

          
ShebangCuándo se usa

          
            
#!/bin/bashLo normal, y lo que hay que saber para el examen. Pide Bash explícitamente, con todas sus extensiones.

            
#!/bin/shPide «un shell POSIX», el mínimo común. En Debian y Ubuntu /bin/sh no es Bash, es dash: más rápido, y sin [[ ]] ni arrays. Un script que funciona con bash puede fallar aquí.

            
#!/usr/bin/env bashBusca Bash en el PATH en vez de fiarse de una ruta fija. Útil en sistemas donde Bash no está en /bin.

            
#!/usr/bin/python3El mecanismo no es de Bash: sirve para cualquier intérprete. Con esta línea el fichero es un programa de Python que se lanza igual.

          
        

      


      

        Sin shebang la cosa funciona… por accidente. Si ejecutas un fichero sin esa línea, el kernel no sabe qué hacer y falla; entonces Bash, que es quien te obedece, tiene una red de seguridad: lo ejecuta él mismo. Parece que todo va bien, hasta que el fichero lo lanza cron, otro shell o un intérprete distinto. Pon siempre el shebang.
      


      
Comentarios

      

        
Salvo en esa primera línea, todo lo que sigue a una # se ignora hasta el final de la línea. Sirve para explicar el porqué de una decisión, no para repetir lo que ya dice el código.

      



#!/bin/bash
# copia-logs.sh — copia los .log de un directorio a ~/copias
# Autor: ana · uso: ./copia-logs.sh /var/log

mkdir -p "$HOME/copias"   # -p: no protesta si ya existe

    


    
    

      
Pruébalo

      
Ejecutarlo: chmod y ese ./

      

        
Un fichero de texto no se ejecuta solo. Hay tres maneras de lanzarlo y no son intercambiables:

      


      

        

          
Forma¿Hace falta +x?Qué ocurre en realidad

          
            

              bash copia.shNo
              Arrancas tú a Bash y le pasas el fichero como argumento, igual que cat recibe un fichero. El shebang se ignora porque ya has elegido el intérprete a mano.
            

            

              ./copia.shSí
              Ejecutas el fichero en sí. Aquí sí manda el shebang, y el sistema exige permiso de ejecución. Es la forma normal.
            

            

              source copia.sh
. copia.sh		No
              Las líneas se ejecutan en tu shell actual, no en uno nuevo. Lo que el script cambie —variables, directorio actual— se te queda puesto al terminar.
            

          
        

      


      

        
El ./ no es decorativo. Cuando escribes un nombre suelto, el shell lo busca en los directorios de la variable PATH, y el directorio actual no está en esa lista —a propósito, para que nadie te cuele un fichero llamado ls en una carpeta compartida. Con ./ le das una ruta explícita: «este de aquí, el del directorio en el que estoy».

        
Y el permiso de ejecución se pone con chmod, el mismo de la guía de permisos:

      



$ chmod +x copia.sh        # añade x a usuario, grupo y otros (según umask)
$ chmod 755 copia.sh       # lo mismo, en octal: rwx para mí, r-x para el resto
$ chmod u+x copia.sh       # solo para el dueño
$ ls -l copia.sh
-rwxr-xr-x 1 ana ana 214 abr 12 10:30 copia.sh
   ↑ esas tres x son lo que faltaba

Guardar y mostrar

      
Variables y echo

      

        
Una variable es un nombre con un valor guardado detrás. Se crea asignando, y se lee poniéndole un $ delante:

      



nombre="Ana"
carpeta=/var/log

echo "Hola, $nombre"          # → Hola, Ana
echo "Miro en ${carpeta}/syslog"  # las llaves separan el nombre de lo que sigue


      

        Sin espacios alrededor del =. Esta es, con diferencia, la equivocación número uno. nombre = "Ana" no asigna nada: el shell lo lee como el comando nombre con dos argumentos, y responde nombre: orden no encontrada. nombre="Ana" pegado, siempre.
      


      

        
Las llaves de ${carpeta} solo hacen falta cuando el nombre toca algo que podría confundirse con él: $carpeta/syslog funciona porque / no puede formar parte de un nombre, pero $nombre_apellido buscaría una variable llamada nombre_apellido. Ponerlas siempre no estorba.

      


      
Las comillas cambian el resultado

      

        
Este es el otro punto donde todo el mundo se quema. Supongamos fichero="mis notas.txt":

      


      

        

          
EscribesSalePor qué

          
            
echo "$fichero"mis notas.txtComillas dobles: sustituye la variable y respeta el valor tal cual, con sus espacios. Es lo que quieres casi siempre.

            
echo '$fichero'$ficheroComillas simples: no sustituye nada. Todo es texto literal.

            
echo $ficheromis notas.txtSe ve igual, pero echo ha recibido dos argumentos y los ha unido con un espacio. Con rm $fichero intentarías borrar dos ficheros que no existen.

          
        

      


      

        Regla de oro: pon comillas dobles alrededor de toda variable que uses como argumento — cp "$origen" "$destino". Cuesta dos caracteres y elimina de golpe la familia entera de fallos por espacios en los nombres.
      


      
De dónde salen los valores

      

        

          
FormaQué hace

          
            
v="texto"Asignación directa. Todo es texto: no hay tipos.

            
read vPide el valor por teclado y lo guarda. read -p "Nombre: " v muestra antes un aviso.

echo: la ventana al interior

      

        
echo imprime sus argumentos y añade un salto de línea. Es trivial, y aun así es la herramienta con la que se depura el 90 % de los scripts: si algo no va, imprime la variable justo antes y mira qué había dentro de verdad.

      



echo "Hola"            # Hola, y salto de línea
echo -n "Sin salto: "  # -n deja el cursor en la misma línea
echo -e "uno\tdos"     # -e interpreta \t (tabulador) y \n (salto)
echo "Estoy en $PWD"   # las variables se sustituyen dentro de las comillas


      

        Para formatos serios existe printf "%s tiene %d años\n" "$n" "$e", que se comporta igual en todos los sistemas. echo -e no es universal; printf sí. Para Linux Essentials basta con echo.
      

    


    
    

      
Pruébalo

      
Argumentos de la línea de comandos

      

        
Un script que siempre hace lo mismo sobre lo mismo sirve de poco. Lo que le da valor es recibir datos al lanzarlo, igual que cp origen destino los recibe.

        
Esos datos llegan en unas variables especiales que Bash rellena solo: $1 es el primer argumento, $2 el segundo, y así hasta donde haga falta. A partir del décimo hay que usar llaves: ${10}.

        
Escribe abajo la línea que lanzarías —con comillas si quieres— y mira qué acaba dentro de cada variable.

      


      

        

          $
          
        

        

          

        

      


      

        Las comillas se las come el shell, no el script. Al escribir "mis notas.txt" le estás diciendo al shell que eso es un argumento aunque lleve un espacio. El script recibe el texto ya limpio, sin comillas. Prueba a quitarlas arriba y verás cómo un argumento se parte en dos.
      


      

        

          
VariableContiene

          
            
$0El nombre con el que se ha llamado al script. Se usa en los mensajes de uso: echo "Uso: $0 fichero".

            
$1 … $9Los argumentos, en orden. Del décimo en adelante, ${10}.

            
$#Cuántos argumentos han llegado. $0 no cuenta.

            
"$@"Todos los argumentos, cada uno como una palabra independiente. Es la forma correcta de reenviarlos a otro comando.

            
"$*"Todos, pero pegados en una sola cadena. Rara vez es lo que quieres.

            
shiftDescarta $1 y desplaza el resto: el antiguo $2 pasa a ser $1. Sirve para ir consumiéndolos en un bucle.

          
        

      


      

        
Un script bien educado comprueba lo primero de todo que le han dado lo que necesita:

      



#!/bin/bash
if [ "$#" -lt 1 ]; then
  echo "Uso: $0 <fichero>"
  exit 2
fi
echo "Trabajando sobre $1"

    


    
    

      
Repetir

      
El bucle for

      

        
Un for repite las mismas órdenes una vez por cada elemento de una lista. Su forma es siempre esta:

      



for variable in lista; do
    órdenes, usando $variable
done


      

        
Las tres palabras for, do y done son obligatorias. El punto y coma antes de do solo hace falta si van en la misma línea; si do va en la línea siguiente, se quita.

        
Lo interesante no es el bucle: es de dónde sale la lista. El shell la construye antes de empezar a iterar, y esa expansión previa explica casi todo lo que sorprende. Elige un caso:

      


      

        

        

          

          

          

        

      


      

        No recorras $(ls). for f in $(ls) parece razonable y se rompe con el primer nombre que lleve un espacio: la salida de ls se trocea por espacios, no por líneas. Con for f in * el shell te entrega los nombres ya separados y enteros. Es más corto y además correcto.
      


      
El pariente cercano: while

      

        
while repite mientras una condición se cumpla, en vez de recorrer una lista conocida. Se usa sobre todo para leer un fichero línea a línea, que es justo lo que for hace mal:

      



while read linea; do
  echo "Leído: $linea"
done < usuarios.txt   # el fichero entra por la entrada estándar del bucle


      

        Para el examen basta con reconocer while y saber que existe. El que hay que saber escribir es for.
      

    


    
    

      
Decidir

      
Lógica básica: if y test

      

        
Aquí hay una idea que, entendida, ordena todo lo demás: en Bash, if no evalúa una expresión: ejecuta un comando y mira si le fue bien.

      



if comando; then
    esto, si el comando terminó bien
else
    esto, si terminó mal
fi


      

        
Por eso funciona if grep -q error registro.log; then … sin ninguna comparación: grep termina bien cuando encuentra algo, y mal cuando no.

        
¿Y las comparaciones normales? También son un comando. [ —sí, el corchete— es un programa cuyo nombre es un corchete, y su último argumento tiene que ser ]. Su forma con nombre legible es test: [ -f x ] y test -f x son idénticos.

      


      

        De ahí que los espacios sean obligatorios. [ "$a" = "b" ] son cinco argumentos separados. ["$a"="b"] es un comando llamado [Ana=b] que no existe. Un espacio después del [, otro antes del ], y otro a cada lado del operador.
      


      

        

          
OperadorCierto cuandoEjemplo

          
            
Ficheros

            
-eexiste (sea lo que sea)[ -e /etc/passwd ]

            
-fexiste y es un fichero normal[ -f "$1" ]

            
-dexiste y es un directorio[ -d /var/log ]

            
-r · -w · -xpuedo leerlo · escribirlo · ejecutarlo[ -x copia.sh ]

            
Texto

            
= · !=las cadenas son iguales · distintas[ "$modo" = "rapido" ]

            
-zla cadena está vacía (zero)[ -z "$1" ]

            
-nla cadena tiene algo[ -n "$RESPUESTA" ]

            
Números

            
-eq · -neigual · distinto[ "$#" -eq 0 ]

            
-lt · -lemenor · menor o igual[ "$n" -lt 10 ]

            
-gt · -gemayor · mayor o igual[ "$n" -ge 1 ]

            
Combinar

            
!niega lo que venga detrás[ ! -d "$1" ]

            
&& · ||y · o, entre dos comprobaciones[ -f x ] && [ -r x ]

          
        

      


      

        = es para texto y -eq para números. No son sinónimos: [ "007" = "7" ] es falso (las cadenas difieren) y [ "007" -eq "7" ] es cierto (los números son el mismo). Es una pregunta clásica.
      


      

        
Con elif se encadenan varias comprobaciones, y el bloque se cierra siempre con fi —if del revés, igual que esac cierra un case:

      



if [ "$#" -eq 0 ]; then
  echo "No me has dicho qué fichero"
elif [ ! -f "$1" ]; then
  echo "$1 no es un fichero"
else
  wc -l "$1"
fi

    


    
    

      
Lo que nadie ve

      
Estado de salida y $?

      

        
Todo comando, al terminar, devuelve al shell un número entre 0 y 255 que dice cómo le fue. Es su estado de salida (exit status), no se imprime en ningún sitio y es la base sobre la que se apoyan if, && y ||.

        
La convención es la contraria de lo que parece lógico:

      


      

        

          
CódigoSignifica

          
            
0Éxito. Hay una sola forma de que algo salga bien, y es el cero.

            
1Fallo genérico. Es el «algo ha ido mal» por defecto.

            
2Uso incorrecto: faltan argumentos, una opción no existe. Convención, no norma.

            
126El fichero se encontró pero no se pudo ejecutar: casi siempre falta el +x.

            
127Comando no encontrado. Un nombre mal escrito, o algo que no está en el PATH.

            
130Lo interrumpiste con Ctrl+C (128 + la señal 2).

          
        

      


      

        
Ese número queda guardado en la variable $?, y ahí es donde está la trampa: $? se refiere siempre al último comando ejecutado, y echo también es un comando.

      



$ ls /etc > /dev/null
$ echo $?
0                       # ls encontró el directorio

$ ls /no-existe 2> /dev/null
$ echo $?
2                       # ls avisa de que no está
$ echo $?
0                       # ¡el 0 es del echo anterior, que funcionó!

$ comandoquenoexiste
bash: comandoquenoexiste: orden no encontrada
$ echo $?
127


      

        Si necesitas el estado dos veces, guárdalo: resultado=$? justo después del comando, antes de hacer nada más. En cuanto ejecutes cualquier otra cosa, $? ya no vale.
      


      
Devolver un estado desde tu script

      

        
exit N termina el script inmediatamente y hace que ese sea el número que reciba quien lo llamó. Si no pones ninguno, el script devuelve el estado de su última orden, que casi nunca es lo que quieres decir.

      



if [ ! -f "$1" ]; then
  echo "No encuentro $1" >&2   # los errores, al canal de errores
  exit 1
fi
# ... el trabajo de verdad ...
exit 0                          # todo bien, dicho explícitamente


      
&& y ||: encadenar según el resultado

      

        

          
EscribesSe lee

          
            
a && bEjecuta b solo si a terminó con 0. «Haz esto y, si sale bien, esto otro.»

            
a || bEjecuta b solo si a falló. «Haz esto o, si no puedes, esto otro.»

            
a ; bEjecuta b siempre, pase lo que pase con a.

            
mkdir d && cd dEntra en el directorio solo si se pudo crear. El idioma más repetido de todos.

          
        

      


      

        Un atajo útil dentro de los scripts: set -e en la segunda línea hace que el script se pare en cuanto un comando falle, en vez de seguir adelante haciendo cosas sobre un estado roto. No entra en el examen, pero explica muchos scripts reales que verás.

Lo que va a pasarte

      
Los ocho errores de siempre

      

        
Casi todos los atascos de un principiante son uno de estos ocho, y se reconocen por el mensaje.

      


      

        

          
El mensajeLa causaEl arreglo

          
            

              bash: ./s.sh: Permiso denegado
              El fichero no tiene el bit de ejecución.
              chmod +x s.sh
            

            

              bash: s.sh: orden no encontrada
              Lo has llamado sin ruta, y el directorio actual no está en el PATH.
              ./s.sh
            

            

              /bin/bash^M: bad interpreter
              El fichero viene de Windows y cada línea acaba en CR LF. Ese ^M sobrante forma parte del nombre del intérprete.
              dos2unix s.sh o sed -i 's/\r$//' s.sh
            

            

              nombre: orden no encontrada
              Espacios alrededor del =: nombre = Ana.
              Pégalo todo: nombre=Ana
            

            

              [: falta «]»
              Falta un espacio dentro de los corchetes, o el propio ].
              Un espacio a cada lado de todo: [ "$a" = "b" ]
            

            

              [: se esperaba un operador unario
              Una variable vacía y sin comillas: [ $v = x ] se queda en [ = x ].
              Comillas siempre: [ "$v" = x ]
            

            

              cp: el destino no es un directorio
              Una variable con espacios sin comillas se ha partido en varios argumentos.
              cp "$origen" "$destino"
            

            

              No sale ningún error, pero no ha hecho nada
              Un cd dentro del script solo afecta al script: se ejecuta en un shell aparte que muere al terminar.
              Si de verdad quieres que te cambie de directorio, ejecútalo con source.
            

          
        

      


      

        La forma rápida de depurar: bash -x s.sh imprime cada línea, ya con las variables sustituidas, justo antes de ejecutarla. Verás al instante que la variable que creías llena estaba vacía.
